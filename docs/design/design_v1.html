3.4 태그 정의와 OR 비트맵 검색

태그는 정의서의 category를 대신하며, 한 항목이 한 태그 안에서 여러 비트를 가질 수 있다. 검색은 "이 비트 중 하나라도 켜진 항목"을 비트 AND 한 번으로 고른다.

필드바이트설명

3.5 관계 정의

관계 정의는 "이 모델의 항목이 어떤 Kind의 항목을 무슨 이름으로 참조하는가"다. 링크 타입 enum과 허용 쌍 검사 코드를 대신한다. 관계가 어떤 참조인지를 정의 자체가 말하므로, 링크 레코드에는 타입이 없다.

필드바이트설명
name64관계 이름. <역할> <대상 Kind 이름> 꼴로 짓는다. 예: "관련 요구사항", "의존 설계 사항"
target_kind4참조하는 Kind
cardinality4MANY 또는 ONE_TO_ONE. 1:1 관계는 확정 조건 검사(R-3)에 쓴다
합계72관계 정의 하나

링크 레코드는 24바이트다. "from의 (relation)은 to다"로 읽는다. 예: "DSN-004의 관련 요구사항은 REQ-002다".

struct RelationRecord
{
    ItemHandle          from;        // 주어
    ItemHandle          to;          // 목적어
    KiottySpecItemKind  model;       // from 의 Kind
    uint32_t            relation;    // 그 모델의 몇 번째 관계 정의인가
};
static_assert(sizeof(RelationRecord) == 24, "unexpected padding");
결정 (2026-11-09, 2차). 관계 이름은 동사("만족시킨다")가 아니라 역할 + 대상 Kind 이름("관련 요구사항")으로 짓는다. 이름만 보고 어느 Kind의 항목이 연결되는지 알 수 있어야 ks의 관계 열 머리글과 --relation 입력이 설명 없이 읽힌다. 역할은 일곱 가지다: 관련(만족시키는 상위 항목, 같은 Kind 끼리의 연관) · 의존 · 검증(테스트가 보는 대상) · 포함(마일스톤) · 대상(결과가 가리키는 계획) · 검사(코드 검사) · 영향(변경 요청). 대상 Kind가 둘이던 정의("만족시킨다 → 요구사항, 외부 인터페이스")는 Kind마다 하나로 나눈다. 정의의 target_kind가 Kind 하나인 것과도 이렇게 맞아떨어진다. 대상 Kind는 주어 모델 자신이어도 된다("관련 요구사항" → 요구사항, "의존 설계 사항" → 설계 사항).
결정 (2026-11-09, 3차). 변경 요청은 소프트웨어의 입력에만 영향을 준다. 입력은 요구사항 · 외부 인터페이스 · 설계 사항 · 개발 수칙이고, 테스트 계획과 결과 같은 출력은 입력이 바뀌면 흐름(Step 5 이후)을 다시 타면서 따라 바뀐다. 그래서 변경 요청의 관계는 "영향" 넷과 일정을 잇는 "관련 마일스톤" 하나만 둔다. 출력 항목에 미치는 영향은 입력 항목에서 관계를 따라 내려가는 영향 탐색(openImpactCursor)으로 구한다.

3.6 태그 레코드

결정 (2026-11-09, 3차). Kind별 고유 필드는 두지 않는다. 항목은 공통 속성 + 태그 레코드 + 본문이고, 항목 사이의 연결은 관계 레코드다. 정의서의 Kind별 데이터(변경 요청의 출처 · 상태 · 진입 단계, 구현 상태, 결과의 PASS / FAIL)는 태그로, 결과가 가리키는 계획은 관계로, 본문 틀 · 로그 · 위반 위치는 본문으로 옮긴다. 태그 값은 RelationRecord와 같은 꼴의 독립 레코드 TagRecord로 둔다.

태그와 관계의 경계. 태그 값은 모델이 미리 정한 이름(비트)의 집합이고, 관계는 다른 항목을 가리킨다. 그래서 "기능 요구사항"은 태그, "REQ-002와 맞물린 요구사항"은 관계다. 같은 Kind 끼리의 연결("관련 요구사항", "의존 설계 사항")도 관계로 표현하며 태그로 흉내 내지 않는다 (3.5).

struct TagRecord
{
    ItemHandle          item;       // 이 태그 값을 가진 항목
    KiottySpecItemKind  model;      // item 의 Kind. 태그 정의를 찾는 모델
    uint32_t            tag;        // 그 모델의 몇 번째 태그 정의인가 (0 ~ 255)
    uint64_t            value;      // 켜진 비트. 하위 48비트만 쓴다
};
static_assert(sizeof(TagRecord) == 24, "unexpected padding");

3.7 본문은 꼭 필요할 때만 읽는다

본문은 토큰이 가장 많이 드는 데이터다(최대 KIOTTY_SPEC_MAX_BODY_LENGTH = 16384 바이트). 그래서 본문을 읽는 길을 하나로 좁힌다.

  • 본문은 항목 ID 하나를 지정해 KiottySpec_readItemBody로만 읽는다. 호출자 버퍼로 읽으며 C 인터페이스 v2 3.6을 따른다.
  • 항목 레코드 · 페이지 · 관계 · 영향 탐색 · 위치 계산 어느 것도 본문을 담거나 끌어오지 않는다. 레코드에는 본문 길이도 넣지 않는다.
  • 여러 항목의 본문을 한 번에 읽는 함수는 두지 않는다.
  • AI는 제목 · 요약 · 태그로 판단할 수 없을 때만 본문을 읽는다. 요약(256바이트)은 본문을 읽지 않아도 판단할 수 있게 쓴다.
  • ks는 본문을 ks item body <ID> 하나로만 보여 준다. 다른 명령은 본문을 출력하지 않는다.

5.3 버전 축과 정리

  • 쓰기는 항상 RUNNING 상태의 가장 최근 체크포인트에 묶인다. DONE인 체크포인트가 가장 최근이면 쓰기 전에 새 체크포인트를 STARTED로 만들어야 한다 (KIOTTY_SPEC_STATUS_CONFIRMED).
  • 항목의 버전은 ItemRecord.checkpoint로 구별한다. 바뀌지 않은 항목은 이전 버전의 체크포인트를 그대로 가리킨다.
  • 현재 위치와 지나온 단계(정의서 4절 "다시 돌아왔을 때")는 저장하지 않고 체크포인트 목록과 변경 요청에서 계산한다(R-12). previous 핸들을 따라가며 같은 단계가 이어지는 구간을 묶는다.
  • 정리(Compaction): 사용자가 DONE 체크포인트 하나를 기준으로 지정하면 그 이전 체크포인트와 거기에만 속한 항목 버전 · 관계 · 결과를 지운다. 가장 최근 DONE은 기준으로만 쓸 수 있다. 정의서 6절 그대로다.

  1. 구간. from과 to는 체크포인트 핸들이며 from.sequence < to.sequence여야 한다. to에 KIOTTY_SPEC_CHECKPOINT_CURRENT(0)를 주면 가장 최근 체크포인트이며, RUNNING 상태의 쓰기도 포함한다. 거꾸로 된 구간은 INVALID_ARGUMENT, 정리로 지워진 체크포인트는 NOT_FOUND다.
  2. 시점의 버전. 체크포인트 c 시점의 항목은 "checkpoint.sequence ≤ c인 버전 중 가장 나중 것"이다. from 시점과 to 시점의 버전을 비교한다.
  3. 알짜 변화만. 구간 안에서 여러 번 바뀌어도 양 끝만 비교한다. 구간 안에서 만들어졌다가 지워진 항목, 고쳤다가 원래대로 돌린 항목은 나오지 않는다. 버전이 달라도 값이 모두 같으면 나오지 않는다.
  4. 변화 종류. from에 없고 to에 있으면 추가, from에 있고 to에서 지워졌으면 삭제, 둘 다 있고 값이 다르면 수정이다. 수정이면 어떤 값이 바뀌었는지 changed_fields 비트로 알려 준다.
  5. Kind 거르기. kind_mask의 비트 (kind − 1)이 켜진 Kind만 본다. 0이면 모든 Kind다. 관계는 주어(from)의 Kind로 거른다.
  6. 값 거르기. field_mask를 주면 그 값이 바뀐 수정만 본다. 예: 본문은 건드리지 않고 제목 · 태그만 바뀐 항목 찾기. 0이면 거르지 않는다. 추가 · 삭제는 언제나 나온다.
  7. 순서. Kind 오름차순, 그다음 ID 오름차순. 페이지를 나눠 읽어도 순서가 같다.
  8. 용량. 결과 행은 커서 풀에 담긴다. max_cursor_rows를 넘으면 CAPACITY_EXCEEDED이며, Kind를 좁혀 다시 연다. 요약은 커서 없이 결과 구조체 하나로 돌려주므로 용량 제한이 없다.

읽는 순서대로 보면 summarizeDiff 한 번으로 바뀐 Kind와 수를 알고, 항목 diff 페이지로 무엇이 어떻게 바뀌었는지 알고, 관계 diff로 연결 변화를 안다. 제목 · 요약 내용은 글자 diff 커서로, 본문은 readItemBodyAt으로만 읽는다.

권장하는 읽는 순서: 요약으로 바뀐 Kind 확인 → 그 Kind만 kind_mask로 항목 diff → 제목 · 요약이 바뀐 것은 글자 diff 커서로 바뀐 글자만 읽기 → 본문은 꼭 필요할 때만 readItemBodyAt.

글자 diff 커서

제목(128바이트)과 요약(256바이트)은 통째로 두 번 보여 주면 토큰이 두 배로 들고, 본문처럼 안 보여 주기에는 짧다. 그래서 이 두 값은 라이브러리가 어느 글자가 더해지고 지워졌는지를 조각으로 돌려주고, 색을 입히는 것은 ks의 output 층이 한다(개발수칙 5.5 "문장은 presentation에서만").

  1. 단위. UTF-8 글자(code point) 단위로 비교한다. 바이트 중간에서 조각이 끊기지 않는다. 입력이 UTF-8이 아니면 저장 단계에서 이미 INVALID_UTF8로 거부되어 있다.
  2. 분석. 두 버전의 최장 공통 부분열(LCS)을 구해 글자마다 UNCHANGED · ADDED · REMOVED를 매기고, 같은 종류가 이어지는 글자는 조각 하나로 합친다. 같은 자리에서 지워지고 더해진 것은 REMOVED 조각 다음에 ADDED 조각이 나온다. 요약이 같으면 UNCHANGED 조각 하나다.
  3. 대상 값. field는 TITLE 또는 SUMMARY 하나다. 본문은 최대 16KB라 LCS 표가 작업 버퍼에 들어가지 않고, 본문 규칙(3.7)에도 어긋나므로 BODY나 비트 둘 이상은 INVALID_ARGUMENT다. 태그 값은 비트 이름을 비교하면 되므로 글자 diff를 쓰지 않는다.
  4. 핸들. 항목은 ID가 아니라 핸들로 받는다. 핸들은 ItemDiff.item이나 findItem(id)로 얻는다. 지금 풀에 없는 항목(구간 뒤에 지워진 항목)은 핸들이 INVALID라 열 수 없으며, 그때는 readItemAt을 두 번 읽어 통째로 비교한다.
  5. 없는 쪽. from 시점에 항목이 없으면(추가) 전부 ADDED, to 시점에 지워져 있으면(삭제) 전부 REMOVED다.
  6. 메모리. 열 때 두 버전(각 최대 256바이트)과 조각 목록(조각마다 어느 버전의 몇 바이트부터 몇 바이트인지, 8바이트)을 커서 풀의 행 공간에 넣는다. 최악 511조각이라 5KB 남짓이며, max_cursor_rows 공간에 들어가지 않으면 CAPACITY_EXCEEDED다. LCS 표는 (글자 수 + 1)² 바이트 이하(최대 64KB)이고 열 때만 컨텍스트 작업 버퍼를 빌려 쓴다. nextTextDiff는 조각 목록을 차례로 읽을 뿐이라 작업 버퍼를 건드리지 않는다.
  7. 구간 규칙. from · to의 조건은 항목 diff와 같다. 항목이 두 시점 모두 없으면 NOT_FOUND다.

저장

DB의 항목 버전 행은 공통 속성, 태그 값, 본문, body_hash(8바이트), 삭제 표시를 체크포인트마다 하나씩 가진다. 바뀌지 않은 항목은 새 행을 만들지 않는다. 관계는 추가 · 삭제한 체크포인트를 행에 남긴다. diff는 이 행들만 읽고 본문 열은 읽지 않는다. 정리(Compaction)로 지운 체크포인트는 비교 구간의 시작으로 쓸 수 없다.

ks diff는 두 가지 모양이다. --kind가 없으면 Kind별 요약 표(summarizeDiff) 하나를 찍고, --kind가 있으면 그 Kind의 바뀐 항목을 추가 · 삭제 · 변경 묶음으로 나눠 찍는다.

ks diff <from> <to> --kind <kind> (--added | --removed | --modified)…
                               [--title] [--summary] [--relations] [--no-color]
입력뜻
--kind필수. Kind 하나. kind_mask로 넘긴다
--added, --removed, --modified필수. 하나 이상을 조합한다. 고른 묶음만 찍는다
--title, --summary선택 열. 주지 않으면 id와 kind만 찍는다
--tag <이름>, --tags태그 열. 이름을 준 태그만, --tags면 그 모델의 모든 태그. 여러 번 줄 수 있다 (8.4)

7. 외부 인터페이스 파일의 처리

결정. Kiotty-Spec은 문서를 관리하지 않는다. .hpp와 .html은 AI가 외부 인터페이스 항목을 질의해서 만드는 산출물이며, Kiotty-Spec이 역으로 그 파일을 읽거나 분석하지 않는다.
사용자외부 인터페이스를 만들거나 고쳐 달라고 요청
→

→
AI외부 인터페이스 항목을 질의해 불러옴
→
AI질의 결과로 .hpp · .html 생성

따라서 다음이 없어진다.

  • 파일 엔티티(FILE-###), 경로 · 해시 추적, "변경됨" 표시 (정의서 2.3).
  • GUI 초안 html의 data-ks-id 스캔과 "html에만 있는 ID / DB에만 있는 뷰" 보고.
  • 인터페이스 파일 · 소스 파일의 구현한다 링크 (정의서 3절).
  • R-9 "인터페이스 파일은 사용자가 요청한 라운드에서만 바뀐다"는 Kiotty-Spec이 검사할 대상이 없어지므로 AI의 작업 규칙으로만 남는다.

소스 파일을 추적하지 않으므로 Step 7의 "구현 완료"는 설계 사항 · 유닛 테스트의 태그 "구현 상태"(3.5)로만 기록한다. 이 범위 결정은 12절에서 확인한다.

8. 질의와 출력

8.1 레코드 페이지만 돌려준다

Markdown 문서를 만드는 기능(context step, context item, context milestone, context cr, rules, pending, status, where 보고서, export markdown, trace, check all 보고서)은 모두 지운다. 라이브러리는 항목 · 관계 · 체크포인트 · 결정 기록의 고정 크기 레코드와 그 페이지만 돌려준다(개발수칙 6.6, 5.5 "문장은 presentation에서만").

ks는 레코드 하나를 TSV 한 줄로 찍는다. 열 순서는 레코드 필드 순서와 같고, 첫 줄은 머리글이다. 핸들은 ID로 바꿔 찍는다.

$ ks item list --kind requirement --tag 요구사항종류=기능
id	kind	title	summary	checkpoint	parent
REQ-001	requirement	로컬 DB에 항목을 저장한다	…	CP-0003	-
REQ-002	requirement	체크포인트로 버전을 나눈다	…	CP-0003	-

8.2 연관 항목은 ID만, 깊이 1

사용자가 따로 묻지 않으면 연관 항목은 ID만 돌려주고 깊이는 1로 제한한다. 관계 커서는 RelationRecord(핸들 두 개와 관계 번호)만 돌려주고, 연관 항목의 제목 · 요약 · 본문을 끌어오지 않는다(본문 규칙은 3.7). 연관 항목의 내용이 필요하면 호출자가 그 ID로 다시 읽는다. 깊이 2 이상의 탐색(영향 항목, 하류 전체)은 depth를 명시해 요청한 경우에만 하며, 결과도 ID 목록이다.

8.3 태그 검색

항목 커서는 Kind 하나와 태그 조건(TagQuery, 3.4) 0 ~ 4개를 받는다. 조건 여러 개는 AND이고, 조건 하나 안의 비트들은 OR이다. 검색은 태그 풀을 처음부터 끝까지 훑으며(개발수칙 3.3) 태그 레코드만 읽는다 (3.6).

8.4 태그 · 관계 열 고르기

모델마다 태그와 관계가 여럿이므로, 항목 목록과 diff에서 보고 싶은 태그 · 관계만 열로 고를 수 있다. 기본은 아무 태그 · 관계 열도 찍지 않는 것이다(8.2 "ID만, 깊이 1"과 같은 이유로 토큰을 아낀다).

입력뜻
--tag <이름>그 이름의 태그 열 하나를 더한다. 여러 번 줄 수 있고 준 순서대로 찍는다. 값은 켜진 비트의 이름을 |로 이은 것, 하나도 없으면 -
--tag <이름>=<비트 이름>[,…]그 태그의 비트가 하나라도 켜진 항목만 고른다(8.3). 거른 태그의 열도 함께 찍는다
--tags모델의 모든 태그 열. 정의 순서
--relation <이름>그 이름의 관계 열 하나를 더한다. 여러 번 줄 수 있다. 값은 대상 ID를 쉼표로 이은 것, 없으면 -
--relations모델의 모든 관계 열. 정의 순서

이름은 모델의 태그 · 관계 이름과 정확히 같아야 하며, 공백이 있으면 따옴표로 감싼다. 없는 이름이면 ks가 "design에 그런 태그가 없다. 있는 것: 설계 종류, 구현 상태"처럼 알려 주고 끝낸다. 이름을 index로 바꾸는 것은 readModel · readTagDefinition · readRelationDefinition이며, 그 뒤는 Kind와 상관없는 같은 함수다(3.6).

관계 열은 항목마다 관계 커서를 여는 대신, openRelationCursorByModel(kind, relation_index)로 그 모델 · 그 관계의 레코드를 from 순서로 한 번에 받아 항목에 나눠 붙인다. 커서는 고른 관계 수만큼만 연다. diff에서는 RelationDiff를 같은 방식으로 나눠 붙인다(5.4).

8.5 커서와 페이지

C 인터페이스 v2 3.5와 같다. 커서를 열면 결과 행의 키가 컨텍스트의 커서 풀에 담기고, 페이지를 가져올 때마다 최대 KIOTTY_SPEC_PAGE_CAPACITY(64)개의 레코드를 호출자가 넘긴 페이지 구조체에 채운다. 커서 수(max_cursors)와 커서당 행 수(max_cursor_rows)는 설정값이며, 넘으면 POOL_IS_FULL · CAPACITY_EXCEEDED다. 4단계에서 만든 CursorPool이 이 역할을 한다.
