# 설계서 v1 구현 계획 (2026-11-09)

대상: [설계서 v1](../design/design_v1.html). C 인터페이스 v2 이행 중 1 ~ 4단계는 끝났다([c_interface_v2.md](../design/c_interface_v2.md)). 이 계획은 남은 5 · 6단계를 설계서 v1에 맞춰 나눈다.

각 단계가 끝날 때마다 빌드(저장소의 build 스킬)와 기존 테스트(`tests/core`, `tests/context`, `tests/datasource`)를 돌린다. 데이터 보존은 jsonl 내보내기 비교로 확인한다.

## 5a. entity와 모델 표

위치: `domain/entity`, `core`

- 고정 크기 레코드를 만들고 `static_assert`로 크기를 고정한다.
  - `ItemRecord` 424바이트
  - `TagRecord` 24바이트 (설계서 3.6)
  - `RelationRecord` 24바이트
  - `CheckpointRecord` 88바이트
  - `DecisionRecord` 2048바이트 상한
- `KiottySpecItemKind`를 13종으로 늘린다. `KiottySpecStep`은 1 ~ 12로 바꾼다.
- `ModelCatalog`를 만든다. Kind별 태그 정의(48비트 비트 이름)와 관계 정의(이름, 대상 Kind, 개수 제한)를 갖는다. 설계서 3.5의 표를 그대로 옮긴다.
  - 변경 요청의 관계는 다섯 개다: 영향 요구사항, 영향 개발 수칙, 영향 외부 인터페이스, 영향 설계 사항, 관련 마일스톤.
  - 요구사항에는 자기 자신을 가리키는 관계 "관련 요구사항"이 있다.
- ID 글자 검사를 넣는다. 허용 글자는 `[A-Za-z0-9_-]`이고 최대 15자다.
- core에 `FixedMap`(정렬 배열 + 이진 탐색)을 추가한다.
- 테스트할 것:
  - 레코드 크기
  - 모델 표 조회
  - ID 검사
  - `FixedMap`

## 5b. repository 합치기

위치: `data/repository`, `data/datasource/schema`

- `ChangeRequestStore`와 `ResultStore`를 `ItemStore`로 합친다. 출처, 상태, 진입 단계 같은 고유 필드는 태그로 옮긴다.
- `MilestoneStore`와 `MilestoneService`를 없앤다. 대신 "포함 설계 사항" · "포함 유닛 테스트" 관계와 태그 "구현 상태"로 표현한다.
- `LinkStore`와 `LinkGraph`는 `RelationStore`로 바꾼다. 허용 쌍은 모델 표의 관계 정의로 검사한다.
- `TagStore`를 새로 만든다. 태그 풀이며 (item index, tag) 순으로 정렬한다.
- `FileStore`, `ProjectFiles`, `scanGuiDraft`, `hashOf`를 지운다.
- 스키마 마이그레이션과 jsonl 가져오기에서 변환할 것:
  - category → 태그 레코드
  - 옛 단계 번호 → 새 번호. 1·2 → 2, 3 ~ 7 → 그대로, 8 → 8·9, 9 → 10, 10 → 11·12
  - note가 64바이트를 넘으면 보고한다.
  - 결정 기록이 2048바이트를 넘으면 보고한다.
- 검증: 이 저장소의 `.kiotty/spec` 데이터를 가져온 뒤 다시 내보낸다. 결과가 변환 규칙과 일치하는지 비교한다.

## 5c. context, 핸들, 공개 헤더

위치: `context`, `include/kiotty_spec.h`, `src/kiotty_spec.cpp`

- `open`에서 현재 버전을 풀에 적재하고 index를 배정한다. 이때 `id_index`, 핸들, generation도 만든다.
- 공개 헤더를 설계서 9절 함수 목록대로 새로 쓴다.
  - `findItem`
  - `setItemTag`, `readItemTag`, `openTagCursor`, `fetchTagPage`
  - 관계 커서, `openRelationCursorByModel`
  - `readItemBody`
- v1 커서를 `CursorPool` 커서 ID로 바꾼다.
- 어댑터를 다시 쓴다. `Result`를 상태 코드로 바꾸는 얇은 층만 남긴다.
- 이 단계부터 기존 `ks` 기준 출력 비교는 쓰지 않는다. Markdown 출력이 없어지기 때문이다.

## 5d. 체크포인트 diff

설계서 5.4 전체를 구현한다.

- 비교 함수:
  - `summarizeDiff`
  - ItemDiff 커서. 레코드는 56바이트이며 현재 항목 핸들을 담는다.
  - RelationDiff 커서
- 과거 시점 읽기: `readItemAt`, `readItemBodyAt`, `readDecisionAt`
- 글자 diff 커서: `openTextDiffCursor(context, item, field, from, to)`, `nextTextDiff`, `closeTextDiffCursor`
  - UTF-8 코드 포인트 단위 LCS로 비교한다.
  - LCS 표는 커서를 여는 동안에만 작업 버퍼를 빌린다.
  - field가 `BODY`이면 `INVALID_ARGUMENT`로 거절한다.
- 테스트 기대값은 설계서 5.4의 호출 예시 블록을 그대로 쓴다. 예시에는 DSN-002, DSN-004, DSN-007, DSN-009와 오류 경우들이 들어 있다.
- 5c와 나눈 이유: diff는 새 API 위에서만 의미가 있고, 가장 복잡한 부분이어서 따로 검증한다.

## 6. `ks` 다시 쓰기와 예외 제거

위치: `app/cli`, 전체

- TSV 출력:
  - `ks diff`는 요약 표를 출력한다.
  - `--kind`와 `--added`/`--removed`/`--modified`를 주면 그룹별 TSV를 출력한다.
  - 바뀐 제목은 `"이전" -> "이후"`로 보여준다.
  - 요약 diff는 색으로 표시한다. 추가는 ESC[94m, 삭제는 ESC[31m이다. 색이 없으면 `{+ +}` / `[- -]`를 쓴다.
- 열 고르기 옵션: `--tag`, `--tags`, `--relation`, `--relations`
- 지울 것:
  - Markdown 생성 계열(`exportMarkdown`, `renderItem`, `traceReport`, `importMarkdown`, `bodyTemplate`)과 md4c 의존성
  - `ContextBuilder`, `StatusBoard`, `queryReadonly`
  - `expect` · `guard`
- `-fno-exceptions`로 빌드한다.
- `docs/deviations.md`에서 해소된 항목을 지운다.

## 남은 확인 사항

- ID에 쓰는 `_`의 Markdown 해석: CommonMark는 단어 중간의 `_`를 강조로 보지 않는다. 그래서 `REQ_003`은 안전하다. `_A_`처럼 `_`로 시작하고 끝나는 ID는 기울임이 된다. 첫 글자를 영문 · 숫자로 제한할지 정해야 한다.
- 설계서 12절 #11: Markdown 양식에 관한 다섯 번째 항목은 메시지가 끊겨 아직 받지 못했다.
