# 설계서 v1 구현 계획 (2026-11-09)

대상: [설계서 v1](../design/design_v1.html). C 인터페이스 v2 이행 중 1 ~ 4단계는 끝났다([c_interface_v2.md](../design/c_interface_v2.md)). 이 계획은 남은 5 · 6단계를 설계서 v1에 맞춰 나눈다.

각 단계가 끝날 때마다 빌드(저장소의 build 스킬)와 기존 테스트(`tests/core`, `tests/context`, `tests/datasource`)를 돌린다. 데이터 보존은 jsonl 내보내기 비교로 확인한다.

## 5a. entity와 모델 표 (완료)

결과: `FixedString`에서 길이 필드를 빼서 `sizeof == Capacity + 1`로 만들었다. 새 레코드와 Kind · Step enum은 `domain/entity`의 `kind.h`, `item_records.h`, `model.h`, `item_id`에 `entity` 이름공간으로 두었다. 옛 `records.h`와 이름이 겹치지 않게 하기 위해서이며, 5b · 5c에서 옛 레코드를 지우면서 합친다. 태그 정의에는 `cardinality`(4바이트)를 더해 3140바이트가 되었다. 변경 요청의 상태와 결과 4종의 결과 태그도 비트 하나만 켜도록 했다. 테스트는 `tests/model`이다.

위치: `domain/entity`, `core`

- 고정 크기 레코드를 만들고 `static_assert`로 크기를 고정한다.
  - `ItemRecord` 424바이트
  - `TagRecord` 24바이트 (설계서 3.6)
  - `RelationRecord` 24바이트
  - `CheckpointRecord` 88바이트
  - `DecisionRecord` 2048바이트 상한
- `KiottySpecItemKind`를 13종으로 늘린다. `KiottySpecStep`은 1 ~ 12로 바꾼다.
- `ModelCatalog`를 만든다 (완료, `domain/usecases/model_catalog`). Kind별 태그 정의(48비트 비트 이름)와 관계 정의(이름, 대상 Kind, 개수 제한)를 갖는다. 설계서 3.5의 표를 그대로 옮긴다.
  - 변경 요청의 관계는 다섯 개다: 영향 요구사항, 영향 개발 수칙, 영향 외부 인터페이스, 영향 설계 사항, 관련 마일스톤.
  - 요구사항에는 자기 자신을 가리키는 관계 "관련 요구사항"이 있다.
- ID 글자 검사를 넣는다. 허용 글자는 `[A-Za-z0-9_-]`이고 최대 15자다. 첫 글자는 `[A-Za-z0-9]`여야 한다.
- core에 `FixedMap`(정렬 배열 + 이진 탐색)을 추가한다.
- 테스트할 것:
  - 레코드 크기
  - 모델 표 조회
  - ID 검사
  - `FixedMap`

## 5b · 5c · 6. 저장소 · 공개 헤더 · `ks` (완료, 한 번에)

사용자 결정(2026-11-09): 옛 공개 API와 `ks`가 옛 저장소에 기대고 있어 5b · 5c · 6을 한 커밋으로 바꿨다. `ks diff`는 5d에서 더한다.

결과:

- 저장소: `MetaStore`(meta, ID 카운터), `CheckpointStore`(index = sequence − 1), `ItemStore`(항목 풀 + 태그 풀 + `FixedMap` ID 색인, 본문은 DB에서만 읽음), `RelationStore`, `DecisionStore`. 옛 store · usecase · `ContextBuilder` · Markdown · md4c · `expect`는 지웠다.
- 스키마 2: `item_version`(summary, body, tags `[[tag, value]]`), `relation_version`(model, relation index), `checkpoint`(state, previous, description), `decision_version`. 쓰기는 가장 최근 체크포인트의 버전 행을 통째로 다시 쓴다.
- 옛 스키마 DB는 열 때 `.kiotty/spec.db.v1`로 옮기고 빈 DB를 만든다. `ks import jsonl`로 다시 채운다.
- usecase: `Lifecycle`(쓰기 묶기, 시작 · 재개 · 완료 · 정리), `Checker`(확정 조건), `Editor`(쓰기 + 구현 완료 → 변경 필요), `Exchange`(jsonl), context의 `Finder`(커서).
- 공개 헤더는 설계서 9절을 따랐다. 설계서에 없던 것을 더했다: `readItemByHandle`(핸들 → ID), `statusName`, `kindName` · `parseKind` · `checkpointStateName`, `initProject`, `readCheckpoint(CURRENT)`, `fetchCheckpointPage`의 핸들 배열, `KiottySpecStepRun`, `importJsonl`의 보고 버퍼.
- `ks`는 TSV를 찍고 예외 없이 빌드한다. 명령 목록은 `ks help`.
- 테스트: `tests/api`(C 인터페이스 처음부터 끝까지).

옛 jsonl 변환 규칙과 이 저장소의 결과(18줄 보고):

## 5b. repository 합치기 (원래 계획)

위치: `data/repository`, `data/datasource/schema`

- `ChangeRequestStore`와 `ResultStore`를 `ItemStore`로 합친다. 출처, 상태, 진입 단계 같은 고유 필드는 태그로 옮긴다.
- `MilestoneStore`와 `MilestoneService`를 없앤다. 대신 "포함 설계 사항" · "포함 유닛 테스트" 관계와 태그 "구현 상태"로 표현한다.
- `LinkStore`와 `LinkGraph`는 `RelationStore`로 바꾼다. 허용 쌍은 모델 표의 관계 정의로 검사한다.
- `TagStore`를 새로 만든다. 태그 풀이며 (item index, tag) 순으로 정렬한다.
- `FileStore`, `ProjectFiles`, `scanGuiDraft`, `hashOf`를 지운다.
- 스키마 마이그레이션과 jsonl 가져오기에서 변환할 것:
  - category → 태그 레코드
  - 옛 단계 번호 → 새 번호. 1·2 → 2, 3 ~ 7 → 그대로, 8 → 8·9, 9 → 10, 10 → 11·12
  - note가 64바이트를 넘으면 보고한다.
  - 결정 기록이 2048바이트를 넘으면 보고한다.
- 검증: 이 저장소의 `.kiotty/spec` 데이터를 가져온 뒤 다시 내보낸다. 결과가 변환 규칙과 일치하는지 비교한다.

## 5c. context, 핸들, 공개 헤더

위치: `context`, `include/kiotty_spec.h`, `src/kiotty_spec.cpp`

- `open`에서 현재 버전을 풀에 적재하고 index를 배정한다. 이때 `id_index`, 핸들, generation도 만든다.
- 공개 헤더를 설계서 9절 함수 목록대로 새로 쓴다.
  - `findItem`
  - `setItemTag`, `readItemTag`, `openTagCursor`, `fetchTagPage`
  - 관계 커서, `openRelationCursorByModel`
  - `readItemBody`
- v1 커서를 `CursorPool` 커서 ID로 바꾼다.
- 어댑터를 다시 쓴다. `Result`를 상태 코드로 바꾸는 얇은 층만 남긴다.
- 이 단계부터 기존 `ks` 기준 출력 비교는 쓰지 않는다. Markdown 출력이 없어지기 때문이다.

## 5d. 체크포인트 diff (완료)

결과:

- `context/differ`: 요약, 항목 diff 커서, 관계 diff 커서, 시점 읽기, 글자 diff 커서. `ks diff`는 `app/cli/diff.cpp`.
- 글자 diff(`core/text_diff`): 글자 단위 LCS 뒤에 두 단계를 더했다. 양옆 편집보다 짧은 공통 구간은 편집에 합치고, 편집 끝이 낱말 가운데이면 공백 경계까지 넓힌다. 순수 LCS로는 설계서 예시의 "로" · 공백이 공통 글자로 잘게 끼어 예시와 다른 조각이 나오기 때문이다. 설계서의 두 예시가 그대로 나오는 것을 `tests/core`에서 확인한다.
- 설계서에 없던 것: `readItemTagAt`(ks diff 의 태그 열이 그 시점의 값을 읽는다). `CursorResult`에는 `page_count`가 없다.
- 본문 비교는 버전 행의 64비트 해시 대신 SQL 안에서 본문 열끼리 비교한다. 본문은 라이브러리 밖으로 나오지 않는다.
- 테스트: `tests/api`의 diff 시나리오(추가 · 삭제 · 수정 필드, 구간 안에서 만들고 지운 항목 제외, field_mask, 관계 diff 순서, 시점 읽기, 글자 diff 조각, 오류 경우).

설계서 5.4 전체를 구현한다.

- 비교 함수:
  - `summarizeDiff`
  - ItemDiff 커서. 레코드는 56바이트이며 현재 항목 핸들을 담는다.
  - RelationDiff 커서
- 과거 시점 읽기: `readItemAt`, `readItemBodyAt`, `readDecisionAt`
- 글자 diff 커서: `openTextDiffCursor(context, item, field, from, to)`, `nextTextDiff`, `closeTextDiffCursor`
  - UTF-8 코드 포인트 단위 LCS로 비교한다.
  - LCS 표는 커서를 여는 동안에만 작업 버퍼를 빌린다.
  - field가 `BODY`이면 `INVALID_ARGUMENT`로 거절한다.
- 테스트 기대값은 설계서 5.4의 호출 예시 블록을 그대로 쓴다. 예시에는 DSN-002, DSN-004, DSN-007, DSN-009와 오류 경우들이 들어 있다.
- 5c와 나눈 이유: diff는 새 API 위에서만 의미가 있고, 가장 복잡한 부분이어서 따로 검증한다.

## 6. `ks` 다시 쓰기와 예외 제거

위치: `app/cli`, 전체

- TSV 출력:
  - `ks diff`는 요약 표를 출력한다.
  - `--kind`와 `--added`/`--removed`/`--modified`를 주면 그룹별 TSV를 출력한다.
  - 바뀐 제목은 `"이전" -> "이후"`로 보여준다.
  - 요약 diff는 색으로 표시한다. 추가는 ESC[94m, 삭제는 ESC[31m이다. 색이 없으면 `{+ +}` / `[- -]`를 쓴다.
- 열 고르기 옵션: `--tag`, `--tags`, `--relation`, `--relations`
- 지울 것:
  - Markdown 생성 계열(`exportMarkdown`, `renderItem`, `traceReport`, `importMarkdown`, `bodyTemplate`)과 md4c 의존성
  - `ContextBuilder`, `StatusBoard`, `queryReadonly`
  - `expect` · `guard`
- `-fno-exceptions`로 빌드한다.
- `docs/deviations.md`에서 해소된 항목을 지운다.

## 확정된 사항

- ID 첫 글자는 영문 대소문자나 숫자로 제한한다. `_A_` 같은 ID가 Markdown에서 기울임으로 바뀌지 않게 하기 위해서다.
- 설계서 12절 #11의 다섯 번째 항목은 네 번째 항목의 앞부분만 반복된 채 끊긴 것이어서 추가 규칙이 없다.
